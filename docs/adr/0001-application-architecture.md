# ADR-0001: アプリケーションアーキテクチャ

- 日付: 2026-08-09
- ステータス: 承認済み
- 対象: このリポジトリのアプリケーション部分のみ

## 背景

TRPG のシナリオとセッションの記録を、これまで Google スプレッドシートで管理してきた。
シナリオの一覧は誰にでも見せたい。
一方でセッションの記録は、一緒に遊んだ人と同じグループの人にだけ見せたい。
1 つのスプレッドシートでは、この 2 つを閲覧者ごとに出し分けられない。

シナリオ側は検索から見つけてほしいので、公開部分はサーバ側で描画して検索エンジンに読ませる必要がある。

画面は、シナリオ一覧、シナリオ詳細、セッション一覧、セッション詳細、プロフィール、管理画面の 6 つ。
シナリオ一覧とシナリオ詳細以外はログインを必要とする。

## 決定

### 全体構成

Rails 8 の SSR モノリスを 1 つ作り、yuno04 の k3s に配置する。
画面は Hotwire (Turbo + Stimulus) で組み、JavaScript は Stimulus の範囲に収める。

| 領域 | 採用するもの |
| --- | --- |
| 言語とフレームワーク | Ruby 3.4 / Rails 8 |
| 画面 | Hotwire (Turbo + Stimulus) + Tailwind CSS |
| データベース | PostgreSQL (CloudNativePG) |
| ファイル保存 | Active Storage + MinIO (S3 互換) |
| 非同期処理とキャッシュ | Solid Queue / Solid Cache |
| 認証 | omniauth-google-oauth2 |
| 認可 | Pundit |
| 管理画面 | Avo |
| テスト | RSpec + FactoryBot + Capybara |
| 静的解析 | RuboCop (rails-omakase) / Brakeman / erb_lint |
| SEO | meta-tags / sitemap_generator / JSON-LD |
| 配布 | GitHub Actions で GHCR へ push |

自前実装は避け、上記の著名ライブラリに寄せる。

### ドメインモデルの骨格

**Person** と **User** を別のモデルにする。

Person は管理者が作る人物であり、セッションの参加者、グループ所属、別名、お気に入りはすべて Person に紐づく。
User は Google アカウントであり、Person に 1 対 1 で紐づく。
この分離により、アカウントを持たない参加者もセッションの記録に残せる。
また、ログイン済みだが Person に紐づいていない User を、公開エリアだけ見える状態として自然に表現できる。

権限 (管理者、GM、プレイヤー) は Person に対して複数付与する。
初期の管理者と GM は 1 人だが、モデル上は最初から複数を許す。

セッションを表すモデルは `PlaySession` と命名する。
`Session` は Rails のセッション機構と名前が衝突するため使わない。

### 可視性の判定

閲覧者の Person が次のいずれかを満たすとき、その PlaySession を閲覧できる。

- その PlaySession の参加者である
- その PlaySession の参加者の誰かと、同じグループに所属している

管理者はすべての PlaySession を閲覧できる。

この判定は Pundit の `Scope` に 1 箇所だけ書き、セッション一覧、セッション詳細、シナリオ詳細に埋め込むセッション履歴のすべてが同じものを使う。
判定が複数箇所に分かれると、片方だけ直して情報が漏れる形になる。

シナリオの準備情報は、ログイン済みかつ本人がネタバレ防止ボタンを押した場合に限り表示する。
押した状態は Person とシナリオの組で永続化し、端末をまたいで引き継ぐ。

### 責務の分界

このリポジトリが持つのは、アプリケーションのコード、Dockerfile、CI、ヘルスチェック、そして必要とする環境変数の仕様までとする。

PostgreSQL、MinIO、Ingress、Cloudflare Tunnel の構成は `yuno04-k3s` リポジトリで管理し、ADR もそちらに置く。
このリポジトリは public であり、クラスタ側の識別子や内部ホスト名を持ち込まない。

### 設定と実行

twelve-factor app に従い、設定はすべて環境変数から読む。
機密は Kubernetes の Secret として与える。
ログは標準出力に出し、収集はクラスタ側の Alloy に任せる。
データベースのマイグレーションはリリース時のジョブとして実行し、アプリケーションプロセスからは分離する。

### 広告と解析

Google Analytics と Google AdSense のタグは、非ログイン時のみ描画する。
ログイン中にタグを出すと、閲覧者と非公開の情報が外部へ渡る。

## 検討した代替案

| 案 | 不採用の理由 |
| --- | --- |
| Rails API + SPA | 公開エリアの SEO を満たすために描画層を別に用意することになり、少人数の開発では割に合わない |
| 静的サイトジェネレータ + 認証プロキシ | セッションの可視性が閲覧者ごとに変わるため、生成物を静的に固定できない |
| SQLite + Litestream | 単一ファイルに集約されるため、ローリング更新と水平スケールが取れない。バックアップも自作になる |
| PVC への直接保存 | Pod とストレージが密結合する。将来の保存先変更も難しい |
| Devise の導入 | パスワードと確認メールの機構を使わないため、設定と依存だけが残る |
| ActiveAdmin | DSL が Hotwire 側と別系統になり、Pundit との連携も薄い |

## 帰結

k3s に PostgreSQL と MinIO という運用対象が 2 つ増える。
どちらも `yuno04-k3s` 側で別の ADR を立てて扱う。

公開エリアと非公開エリアが 1 つのプロセスに同居するため、認可の漏れがそのまま情報漏えいになる。
これに対しては、可視性の判定を 1 箇所に集約したうえで、各エンドポイントの request spec で未ログイン、Person 未紐づけ、グループ外、グループ内、管理者の 5 通りを検証する。

MinIO に置いた画像は公開エリアからも参照される。
バケットの公開範囲と配信経路をクラスタ側で設計する必要がある。

## 将来の拡張

次の 2 つは今回の実装対象に含めないが、モデルがこれらを阻害しないようにする。

- セッション登録時の Discord への通知。Solid Queue のジョブとして追加する
- 本人による Google アカウントの差し替え。User と Person が分かれているため、User 側の `google_uid` の更新で足りる
