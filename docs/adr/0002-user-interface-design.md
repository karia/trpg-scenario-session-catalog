# ADR-0002: ユーザーインターフェースの刷新

- 日付: 2026-08-22
- ステータス: 承認済み
- 対象: 公開画面、ログイン後の画面、管理画面

## 背景

現在の画面は、フォーム要素や操作ボタンのスタイルを各テンプレートに直接記述している。
同じ役割の部品でも画面ごとに表現が異なり、変更時に複数箇所を揃える必要がある。

デザイントークンは `app/assets/tailwind/application.css` の `@theme` に 6 色あるが、いずれも明るい紙面を前提にした値である。
入力欄の面を表す色も、検証エラーや危険操作を表す色も持っていない。

スマートフォンやタブレットからの利用も多い。
現在の表や横並びのフォームは、狭い画面で横スクロールや過密な配置を生じやすい。

## 決定

サイト全体を、黒を基調とするダークデザイン「Obsidian Glass」へ刷新する。
ライトテーマは提供しない。
単一の配色と共通 UI 部品を全領域で使い、画面幅に応じて情報の配置を変える。

実装は一括で置き換えず、[実装計画](../plans/2026-08-22-ui-redesign.md) の単位で PR に分ける。
移行中は新旧の画面が混在するが、共通方針は最初の PR で固定する。

### デザイン案の選定

[デザインサンプル](https://karia.github.io/misc-html/design-sample/)として 11 案を作って比較した。
このうちダークな案は Graphite Ledger、Obsidian Glass、Mono Brutal、Carbon Studio の 4 案である。

一覧の主役はシナリオのジャケット画像であり、画像の色を情報面が邪魔しないことを重視した。
半透明の面を黒地の上に重ねる Obsidian Glass は、面の輪郭を保ったままジャケットの色を素通しできるため、この点で他の 3 案より適する。

### 採用する配色

| 役割 | 値 | 補足 |
| --- | --- | --- |
| 背景 | `#050608` | |
| 情報面 | `#12161c` 不透明度 80% | ぼかし 20px |
| 入力面 | `#090c10` 不透明度 80% | |
| 控えめな面 | `#1a2029` | 不透明 |
| 境界 | `#35404e` | |
| 本文 | `#f4f7fb` | |
| 補助情報 | `#a5afbd` | |
| 主要操作 | `#c7ddf7` | 上に載る文字は `#07101a` |
| 強調 | `#9284ff` | 上に載る文字は `#080612` |
| フォーカス | `#a9ceff` 不透明度 21% | |

角丸は面が 30px、カードが 26px、操作要素が 14px。
ヘッダーは `#080a0d` 不透明度 80% にぼかし 18px を重ねて固定する。

サンプルは危険操作と検証エラーの色を持たない。
この 2 つは背景に対して WCAG 2.2 AA のコントラストを満たす値を新たに選ぶ。

本文と補助情報のコントラストは、背景に対しても情報面に対しても 7 を超える。
一方、境界の `#35404e` は背景に対して 1.9、情報面に対して 1.7 であり、非テキストのコントラストに求められる 3 に届かない。
面どうしの色差も、背景と情報面で 1.1、情報面と入力面で 1.1、背景と控えめな面で 1.2 しかない。
面の塗り分けでは輪郭を示せないため、入力欄のように境界だけが要素の輪郭を示す部品には、明るい境界色を別に用意する。

## 共通方針

### 視覚表現

- 色、余白、角丸、境界線、影、文字サイズをデザイントークンとして一元化する
- 半透明とぼかしは階層を示す面に限定し、本文や入力欄の可読性を損なわない
- 本文、補助情報、操作ラベルに 13px 未満の文字を使わない。Tailwind のスケールでは `text-xs` が 12px にあたるため、これを使わない
- 色だけで状態を区別せず、ラベルまたはアイコンを併用する

### レスポンシブ

- PC では一覧性を優先し、カードグリッドや複数カラムを使う
- スマートフォンではジャケットを上、情報を下に積んだカードへ切り替える
- 操作メニューを横スクロールさせない。絞り込み条件が多い場合は折り畳む
- 表は比較が必要な画面に限り、スマートフォンではカードまたは定義リストへの切り替えを優先する
- ブレークポイントは端末名ではなく、内容が過密になる幅を基準に選ぶ

### 共通 UI 部品

- ボタン、フォーム、通知、バッジ、カード、空状態、ページ見出しを共通化する
- 通常、hover、focus、disabled、error、danger の状態を部品側で定義する
- 画面固有のクラス列で共通部品の見た目を上書きしない
- field 部品がラベル、必須表示、説明、入力要素、検証エラーを 1 つのまとまりとして描画し、説明とエラーを `aria-describedby` で入力要素に関連付ける
- 画面遷移にはリンク、状態変更にはボタンを使い、見た目だけを理由に要素の意味を入れ替えない

### アクセシビリティ

- WCAG 2.2 AA のコントラストとキーボード操作を満たす
- タップ対象は原則 44px 以上とする。WCAG 2.2 AA の下限は 24px だが、それを上回る自主基準として置く
- フォーカス表示を消さない
- `prefers-reduced-motion` では装飾的なアニメーションを抑制する
- 対応ブラウザでは `prefers-reduced-transparency` を尊重する

## 実装上の制約

次の 5 つは、実装の順序を問わず全期間にわたって守る。

### 既存トークンを書き換えない

Tailwind CSS v4 を継続して使い、トークンは `@theme` に役割名で定義する。

新しいトークンは、既存の `ink`、`paper`、`surface`、`seal`、`muted`、`rule` とは別名で追加する。
既存トークンの値は移行期間中に変更しない。
これらは未移行の全画面が参照しており、値を反転させると、たとえば白い面の上の本文が明色になって読めなくなる。
旧トークンは移行完了後の PR で削除する。

既存の共有部分テンプレート (`shared/_delete_button` など) も同様に書き換えない。
複数のタスクにまたがって使われているため、先に着手した PR が書き換えると、その PR の確認範囲外の画面が同時に変わる。
呼び出し側を新しい部品へ差し替え、消費者がなくなった時点で削除する。

### ブラウザ描画の UI もダークにする

base layer の `color-scheme` を `dark` にする。
これを切り替えないと、日時入力、select、スクロールバーが明色のまま暗い画面上に残る。

重なり順は `@theme` の名前空間に存在しないため、素のカスタムプロパティとして持ち、任意値記法で参照する。

半透明の情報面には、不透明な背景色をフォールバックとして先に指定する。
ぼかしを使えない環境でも、情報の境界とコントラストを保つ。

### 部品に装飾を渡さない

共通部品は `app/views/shared/ui` 配下の部分テンプレートと専用ヘルパーで実装する。
状態を持たない表示のために、新しいコンポーネントライブラリは導入しない。

部品が受け取るのは、文言、variant、サイズ、状態、そして `id`、`data-*`、`aria-*` に限る。
`class` は受け取らない。
HTML 属性をまとめて受け取る形にすると、`class` 経由で共通部品の見た目を上書きできてしまう。

Turbo で更新する範囲は部品の外側で定め、Stimulus は開閉、並べ替え、自動送信など、ブラウザ上の振る舞いだけを担当する。

### DOM を重複させない

マークアップはモバイルファーストで作り、原則として同じ DOM を CSS Grid と Flexbox で再配置する。
JavaScript で PC 用とスマートフォン用の DOM を切り替えない。

重複を許すのは、表からカードへの変換のように情報の読み順が変わる場合に限る。
重複させる側には `id` を持たせない。
同じ `id` が 2 つあると、`aria-describedby` による説明とエラーの関連付けが最初の 1 つしか効かなくなる。

### アクセシビリティを機械で確認する

各移行 PR で、対象画面の system spec に axe による自動チェックを入れる。
コントラストとラベルの関連付けは手作業の確認から漏れやすく、11 回の移行で漏れが蓄積する。

見た目そのものはテストへ固定しない。

## 検討した代替案

### 現在の配色を保って部品だけ共通化する

実装量は抑えられるが、サイトの印象を変えるという目的を満たさないため採用しない。

### 画面ごとにデザインを最適化する

個々の画面では調整しやすいが、同じ操作の表現が再び分散するため採用しない。

### ライトテーマとダークテーマを同時に提供する

初回の刷新で 2 つの配色と状態を検証すると、各 PR の範囲が広がるため今回は扱わない。
将来追加する場合は、役割名のトークンを `:root` と `prefers-color-scheme` の 2 組に分けて定義する。
今回定義するのはダークの 1 組だけであり、役割名にしただけでは自動的にテーマ化できない。

## 帰結

最初に共通部品を用意するため、利用者から見える変化より先に基盤の PR が必要になる。
その後は画面群ごとに移行でき、各 PR の変更範囲と確認対象を限定できる。

移行が終わるまで、新旧 2 組のトークンと、新旧 2 つの共有部品が並存する。
どちらを使うかは画面が移行済みかどうかで決まり、最後の PR まで判断が必要になる。

ダークデザインでは低コントラストになりやすいため、各画面の完了条件にコントラストとフォーカス表示の確認を含める。

広告は Google AdSense が描画するため、こちらの配色を適用できない。
明るい広告が暗い画面上で浮くことを避けられず、枠の余白と境界で緩和するにとどまる。

メール本文は対象に含めない。
`app/views/layouts/mailer.html.erb` はスタイルを持たず、メールクライアント側では外部スタイルシートも `backdrop-filter` も使えないため、共通部品を共有できない。

PWA の manifest と service worker も対象に含めない。
`config/routes.rb` で PWA のルートがコメントアウトされており、`manifest.json.erb` の明るい配色は利用者に届いていない。
