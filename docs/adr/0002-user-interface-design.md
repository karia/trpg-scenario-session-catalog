# ADR-0002: ユーザーインターフェースの刷新

- 日付: 2026-08-22
- ステータス: 承認済み
- 対象: 公開画面、ログイン後の画面、管理画面

## 背景

現在の画面は、フォーム要素や操作ボタンのスタイルを各テンプレートに直接記述している。
同じ役割の部品でも画面ごとに表現が異なり、変更時に複数箇所を揃える必要がある。

スマートフォンやタブレットからの利用も多い。
現在の表や横並びのフォームは、狭い画面で横スクロールや過密な配置を生じやすい。

複数のデザイン案を比較し、黒を基調とする[「Obsidian Glass」](https://karia.github.io/misc-html/design-sample/obsidian-glass.html)を採用することにした。

## 決定

サイト全体を「Obsidian Glass」に基づくダークデザインへ刷新する。
単一の配色と共通UI部品を全領域で使い、画面幅に応じて情報の配置を変える。

実装は一括で置き換えず、後述する画面群ごとのPRに分ける。
移行中は新旧の画面が混在するが、共通方針は最初のPRで固定する。

## 共通方針

### 視覚表現

- 背景は黒に近い寒色、情報面は青みのある濃い灰色、主要操作は淡い青を使う
- 半透明とぼかしは階層を示す面に限定し、本文や入力欄の可読性を損なわない
- 色、余白、角丸、境界線、影、文字サイズをデザイントークンとして一元化する
- 本文、補助情報、操作ラベルには13px未満の文字を使わない

### レスポンシブ

- PCでは一覧性を優先し、カードグリッドや複数カラムを使う
- スマートフォンではジャケットを上、情報を下に積んだカードへ切り替える
- 操作メニューを横スクロールさせない。絞り込み条件が多い場合は折り畳む
- 表は比較が必要な画面に限り、スマートフォンではカードまたは定義リストへの切り替えを優先する

### 共通UI部品

- ボタン、フォーム、通知、バッジ、カード、空状態、ページ見出しを共通化する
- 通常、hover、focus、disabled、error、dangerの状態を部品側で定義する
- 画面固有のクラス列で共通部品の見た目を上書きしない

### アクセシビリティ

- WCAG 2.2 AAのコントラストとキーボード操作を満たす
- タップ対象は原則44px以上とし、フォーカス表示を消さない
- 色だけで状態を区別せず、ラベルまたはアイコンを併用する
- `prefers-reduced-motion`では装飾的なアニメーションを抑制する

## UI実装の構成

### スタイルとデザイントークン

Tailwind CSSを継続して使い、色、文字、余白、角丸、境界線、影、重なり順をテーマ変数として定義する。
トークンは具体的な色名ではなく、背景、情報面、本文、補助情報、境界、主要操作、危険操作という役割で命名する。
これにより、配色の調整をテンプレートの変更から分離する。

基本要素の既定値とフォーカス表示はTailwindのbase layerに置く。
共通部品のスタイルはcomponent layerに置き、各画面のテンプレートは配置と部品のvariantだけを指定する。
任意の色や余白を表す値は、試作時の調整を除いてテンプレートへ直接記述しない。

半透明の情報面には、不透明な背景色をフォールバックとして先に指定する。
ぼかしを使えない環境や`prefers-reduced-transparency`を指定した環境でも、情報の境界とコントラストを保つ。

### 部品の実装方法

共通部品は`app/views/shared/ui`配下の部分テンプレートと専用ヘルパーで実装する。
部品の引数は、文言、variant、サイズ、状態、追加のHTML属性に限定する。
呼び出し側から任意の装飾クラスを渡すAPIは設けない。

状態を持たない表示のために、新しいコンポーネントライブラリは導入しない。
Turboで更新する範囲は部品の外側で定め、Stimulusは開閉、並べ替え、自動送信など、ブラウザ上の振る舞いだけを担当する。
JavaScriptでPC用とスマートフォン用のDOMを切り替えない。

部品は次の単位で用意する。

| 分類 | 部品 |
| --- | --- |
| 操作 | primary、secondary、dangerのボタン、アイコン付きボタン、テキストリンク |
| フォーム | field、input、textarea、select、checkbox、radio、エラー要約、送信操作 |
| 情報表示 | badge、alert、toast、empty state、definition list、pagination |
| 構造 | page header、section、card、dialog、disclosure、navigation |
| ドメイン | シナリオカード、セッションカード、人物カード、絞り込みパネル |

ドメイン部品は操作部品、フォーム部品、情報表示部品を組み合わせる。
ドメイン部品の都合で基本部品の見た目を複製しない。

### フォームの契約

field部品がラベル、必須表示、説明、入力要素、検証エラーを一つのまとまりとして描画する。
説明とエラーは`aria-describedby`で入力要素に関連付け、検証失敗時も入力値とラベルを保持する。
入力要素の高さ、余白、角丸、文字サイズ、disabledとerrorの表現はフォーム部品間で揃える。

破壊的操作にはdanger variantと確認を使う。
画面遷移にはリンク、状態変更にはボタンを使い、見た目だけを理由に要素の意味を入れ替えない。
繰り返し入力は1項目を一つのまとまりとし、追加と削除の操作をその項目の近くに置く。

### レスポンシブ実装

マークアップはモバイルファーストで作り、原則として同じDOMをCSS GridとFlexboxで再配置する。
ブレークポイントは端末名ではなく、内容が過密になる幅を基準に選ぶ。
PC専用とスマートフォン専用のマークアップを重複させるのは、表からカードへの変換など、情報の読み順が変わる場合に限る。

一覧カードは、狭い画面ではジャケット、見出し、主要情報、補助情報、操作の順に縦へ積む。
広い画面では同じ情報をグリッドへ再配置する。
人数とゲームシステム名は補助情報であっても13px未満にせず、長い名称は省略だけに頼らず折り返せるようにする。

絞り込みは、狭い画面では開閉できるパネルへ収め、適用中の条件数と解除操作を閉じた状態でも表示する。
主要な検索語と適用操作はパネル外に残し、横スクロールする操作列を作らない。

### 検証方針

基本部品は、通常、操作中、disabled、error、長い文言、項目なしの状態を確認する。
各画面の移行PRでは、少なくとも320px、768px、1280px相当の表示幅で、横方向のはみ出し、読み順、タップ領域を確認する。
フォームと主要な操作経路はCapybaraのsystem specで保護し、見た目だけの差分をテストへ固定しない。
色のコントラスト、キーボード操作、フォーカス表示は各移行PRで確認し、最後の監査PRで画面間の差異を確認する。

## 実装タスク

各行を1タスク、1PRとして実施する。
後続タスクで新しい共通部品が必要になった場合は、その画面だけで作らず、同じPRで共通部品へ追加する。
各画面の移行PRでは、共通方針に定めたアクセシビリティ要件も完了条件に含める。

| 順序 | PRの対象 | 依存 | 完了条件 |
| --- | --- | --- | --- |
| 1 | デザイントークンと基本UI部品 | なし | デザイントークンとボタン、フォームなどの基本部品を利用できる |
| 2 | アプリケーション枠、ヘッダー、ナビゲーション、通知 | 1 | 全画面の外枠とモバイルナビゲーションが新デザインになる |
| 3 | シナリオ一覧、カード、絞り込み | 1、2 | PCとスマートフォンで別のカード配置を使い、絞り込みに横スクロールがない |
| 4 | シナリオ詳細 | 1、2 | ジャケット、基本情報、本文、限定情報が新デザインになる |
| 5 | シナリオ登録・編集 | 1、2 | フォーム項目、エラー、保存操作が共通部品へ移行する |
| 6 | セッション一覧・詳細 | 1、2 | 日程、参加者、録画情報が画面幅に応じて再配置される |
| 7 | セッション登録・編集 | 1、2、6 | 日程と参加者の繰り返し入力が狭い画面でも1列で操作できる |
| 8 | 人物・ユーザー関連画面 | 1、2 | 一覧、詳細、編集で共通UIを使い、モバイルでも操作できる |
| 9 | 作者・ゲームシステム関連画面 | 1、2 | 一覧と管理画面で共通UIを使い、モバイルでも操作できる |
| 10 | グループ・サイト設定などの管理画面 | 1、2 | 管理画面で共通UIを使い、モバイルでも操作できる |
| 11 | 全画面のアクセシビリティ監査と旧スタイルの整理 | 3〜10 | 各移行PRの確認結果を横断監査し、未使用の旧スタイルを削除する |

## 検討した代替案

### 現在の配色を保って部品だけ共通化する

実装量は抑えられるが、サイトの印象を変えるという目的を満たさないため採用しない。

### 画面ごとにデザインを最適化する

個々の画面では調整しやすいが、同じ操作の表現が再び分散するため採用しない。

### ライトテーマとダークテーマを同時に提供する

初回の刷新で二つの配色と状態を検証すると、各PRの範囲が広がるため今回は扱わない。
将来追加する場合も、同じデザイントークンと共通UI部品を使う。

## 帰結

最初に共通部品を用意するため、利用者から見える変化より先に基盤のPRが必要になる。
その後は画面群ごとに移行でき、各PRの変更範囲と確認対象を限定できる。

移行中は新旧デザインが混在する。
共通のアプリケーション枠を先に移行し、混在期間でもナビゲーションと通知の操作方法は揃える。

ダークデザインでは低コントラストになりやすいため、各画面の完了条件にコントラストとフォーカス表示の確認を含める。
